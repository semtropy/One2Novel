# One2Novel 项目：大白话详解

> 写给不懂技术的人也能看懂——这个项目到底干了什么，每个部件怎么转起来的。

---

## 一、这个项目到底是干嘛的？

简单说：**这是一个帮人写网线的 AI 工具。**

你输入一句灵感（比如"一个废柴少年捡到了一把断剑"），它能帮你生成整本小说——从故事大纲、角色设定、世界观，到一章一章写正文。

但它不只是"你让我写我就写"那么简单。它要解决的核心问题是：

**网文动辄百万字，写到第 200 章的时候，AI 不可能记得第 3 章说过什么。** 这就导致角色会忘记自己叫什么、前面埋的伏笔会断掉、世界观会自相矛盾。

这个项目就是为了解决这个"长文记忆"问题而设计的。

---

## 二、整个系统的骨架

```
┌─────────────────────────────────────────────┐
│  前端界面（你看到的）                          │
│  React 做的网页/桌面软件                       │
│  左边：章节目录  中间：编辑器  右边：工具箱     │
└──────────────────┬──────────────────────────┘
                   │  你点"写一章"
                   ▼
┌─────────────────────────────────────────────┐
│  后端服务（真正干活的）                         │
│                                             │
│  第一步：攒上下文（拼凑所有需要的参考资料）       │
│  第二步：交给 AI 写正文                       │
│  第三步：AI 自己批改作业（10 个维度打分）       │
│  第四步：不及格就自动重修（修复）              │
│  第五步：保存 + 把学到的知识记到"笔记本"里      │
└─────────────────────────────────────────────┘
```

## 三、记忆系统——AI 的"笔记本"

### 3.1 它记了什么？

想象你在读一本百万字的玄幻小说，你需要记住的东西大概分这几种：

| 记忆类型 | 例子 | 重要性 |
|---------|------|--------|
| **世界规则** | "这个世界的修炼体系分九重天，突破时需要渡劫" | 永远不能忘 |
| **角色状态** | "张三现在受了重伤，在青云宗养伤" | 每章都可能变 |
| **角色关系** | "李四和王五是师徒，但李四怀疑王五背叛" | 慢慢变化 |
| **伏笔/线索** | "第 15 章埋了一个关于神秘组织的伏笔，还没回收" | 必须记住，后面要回收 |
| **关键事件** | "第 30 章发生了宗门大战，赵六死了" | 记住发生过什么 |
| **时间线** | "事件发生在春季，距离大比还有 3 天" | 保证时间不乱 |

这些东西都存在一个叫 `MemoryItem` 的表里。每条记忆有 5 个字段：

- **类别**（category）：上面那 6 种之一
- **主体**（subject）：谁的事？比如"张三"
- **字段**（field）：什么事？比如"currentStatus"（当前状态）
- **值**（value）：具体内容，比如"重伤中"
- **来源章节**（sourceChapter）：第几章学到的这条记忆

### 3.2 怎么记的？（写后沉淀）

每次写完一章，系统会自动"消化"这一章的内容，提取出有价值的信息存进笔记本。这个过程叫**沉淀**。

**具体流程：**

```
你写完第 N 章
    │
    ▼
系统触发一个事件："postWrite.chapterSaved"
    │
    ├──→ 同时启动 11 个后台任务（像餐厅后厨同时备 11 道菜）
    │    │
    │    ├──→ 提取时间线事件
    │    ├──→ 生成章节摘要
    │    ├──→ 存入 RAG 检索库（后面细说）
    │    ├──→ 每 10 章压缩一次前面的内容
    │    ├──→ 检测 AI 写作痕迹
    │    ├──→ 更新角色状态
    │    ├──→ 记忆沉淀 ← 这里！
    │    ├──→ 检查伏笔有没有过期
    │    ├──→ 检查小说是不是快写完了
    │    ├──→ 卷完结时做跨卷审计
    │    └──→ 债务利息计算（欠读者的爽点要还）
    │
    └──→ 不管哪个任务失败都不影响写下一章
```

**记忆沉淀是怎么提取的？**

关键创新：**不额外花 AI 的钱。**

之前系统写一章已经调了 2 次 AI：
1. 第一次：更新角色状态（`characterStateUpdater`）
2. 第二次：生成章节摘要（`generateChapterSummary`）

`writeMemories()` 这个函数把这 2 次 AI 的输出**直接拿来用**，从中提取结构化事实存进 `MemoryItem` 表。不需要再调一次 AI。

提取规则很简单——就像人做笔记一样：

- 角色状态变了？→ 记一条 `character_state`
- 章节摘要里有重大事件？→ 记一条 `story_fact`
- 揭示了新的世界观？→ 记一条 `world_rule`
- 有没回收的伏笔？→ 记一条 `open_loop`

### 3.3 怎么用的？（写前注入）

下次写新章节之前，系统会把笔记本翻出来给 AI 看。

**具体流程：**

```
你要写第 N 章
    │
    ▼
系统去 MemoryItem 表里查：
    │
    ├── 世界规则（world_rule）→ 无条件加载，永远有效
    │   例："修仙者突破需要渡劫"
    │
    ├── 其他记忆 → 只看最近 50 章的
    │   例：第 48 章张三受了重伤
    │
    ├── 按优先级排序：
    │   世界规则 > 伏笔 > 角色状态 > 关系 > 读者承诺 > 事件 > 时间线
    │
    ├── 限制数量：
    │   世界规则+伏笔最多 10 条
    │   其他记忆最多 25 条
    │
    └── 格式化后塞给 AI："以下事实你必须遵守"
```

### 3.4 去重策略

如果第 50 章说"张三在青云宗"，第 60 章说"张三去了魔教"，系统怎么处理？

**规则：新的覆盖旧的，但旧的不会被删掉。**

1. 查到同一条记忆（同样的类别+主体+字段）
2. 把旧的标记为 `outdated`（过时了）
3. 插入新的值
4. 旧数据留着当审计记录，方便回溯

### 3.5 复活问题

如果角色在第 50 章死了，第 100 章又复活了（玄幻常见操作），当前系统有一个小漏洞：

- `EntityLifecycle` 表会记录"张三 第50章 死亡"
- 但 `MemoryItem` 的 `character_state` 只会更新状态为"活着"
- 中间缺少一个"证据链"说明为什么从死变活

改进方案：利用 `evidence` 字段（目前是空的）记录死亡事件，复活时引用它。

## 四、RAG 检索系统——AI 的"搜索引擎"

### 4.1 什么时候检索？

**写每一章之前。** 系统在拼凑上下文的时候，会同时发起语义搜索。

### 4.2 检索什么内容？

不是搜关键词，而是**搜意思**。比如你要写"张三和李四打架"，系统会去以前所有章节里找"类似的战斗场景"、"张三之前的招式"、"李四的性格特点"等等。

具体来说搜三类东西：

1. **语义搜索**（`rag_semantic_context`）：根据本章的任务、标题、伏笔、爽点类型，生成多个搜索词，去以前的章节里找意思相关的内容
2. **回溯搜索**（`rag_backtrack_context`）：如果本章属于某个场景，就去这个场景对应的卷摘要里找相关内容
3. **风格样本**（`rag_style_samples`）：找以前写得好的段落做风格参考

### 4.3 怎么存的？

每写完一章，系统自动把章节内容切成小块存起来：

```
第 N 章正文（5000字）
    │
    ├── 存一个摘要 chunk（~200字）
    │
    └── 按句子切分，每 1500 字存为一个场景 chunk
        最多存 20 个场景 chunk
```

### 4.4 怎么搜的？（混合搜索）

系统用了**两层搜索 + 融合**的策略：

```
搜索请求："张三和李四打架"
    │
    ├── 第一层：向量搜索（语义相似）
    │   把搜索词变成数字向量 → 跟库里所有 chunk 的向量比相似度
    │   模型：DeepSeek bge-m3（首选）→ OpenAI → Qwen
    │
    ├── 第二层：BM25 搜索（关键词匹配）
    │   把搜索词拆成关键词 → 找包含这些词的章节
    │   不依赖 AI 模型，随时可用
    │
    ├── 融合：RRF（倒数秩融合）
    │   把两层搜索结果按排名加权合并
    │   公式：score = 1/(60 + rank)
    │   两层都高的 chunk 会排在最前面
    │
    └── 精排：rerank
        用 AI 模型对融合后的结果再做一次精细排序
        如果 rerank API 挂了 → 退回字符重叠打分
```

### 4.5 降级策略

系统非常注重**不能因为 AI 挂了就没法用**：

| 情况 | 降级方案 |
|------|----------|
| Embedding API 挂了 | 只用 BM25 搜索，内容照样存 |
| Rerank API 挂了 | 用字符重叠打分代替 |
| 单次搜索超时 | 跳过这一路，用剩下的结果 |

### 4.6 存在哪？

存在一个独立的 SQLite 文件 `rag_vectors.db` 里，两张表：
- `vectors`：chunk 内容 + 向量（如果有的话）
- `bm25_index`：关键词倒排索引

## 五、Agent 协作——AI 的"质检团队"

### 5.1 三个 Agent 分别干什么？

系统里有三个"AI 员工"，各司其职：

| Agent | 岗位 | 干什么 | 温度 |
|-------|------|--------|------|
| **ContextAgent** | 策划 | 读完所有参考资料后，总结出一份"本章写作任务简报" | 0.3（严谨） |
| **ReviewerAgent** | 质检员 | 看完 AI 写的章节，从 10 个维度打分 | 0.3（严谨） |
| **DataAgent** | 数据分析师 | 从写好的章节里提取结构化事实（角色变化、事件等） | 0.3（严谨） |

### 5.2 它们是怎么协作的？

**不是同时开工，而是一个接一个来（流水线）：**

```
第 N 章写作全流程：
    │
    ├─ ① ContextAgent：先看所有参考资料，出一份"写作简报"
    │   内容：本章要讲什么、角色什么状态、用什么风格
    │   ↓
    ├─ ② Writer（主 AI）：拿着简报写正文
    │   ↓
    ├─ ③ ReviewerAgent：批改作业，10 个维度打分
    │   ↓
    ├─ ④ 如果分数不够 → 修理工介入（见下文）
    │   ↓
    ├─ ⑤ DataAgent：从定稿里提取结构化事实
    │   ↓
    └─ ⑥ Projection Writers：把事实分发到各个"仓库"
        ├─ 状态仓库：更新角色当前状态
        ├─ 索引仓库：建立章节索引
        ├─ 摘要仓库：生成章节摘要
        ├─ 记忆仓库：写入 MemoryItem
        └─ 向量仓库：存入 RAG 系统
```

### 5.3 10 维质检是怎么打的？

质检员从这 10 个方面给章节打分（每项 1-10 分）：

| 维度 | 问的是什么 | 归类 |
|------|-----------|------|
| 开头吸引力 | 第一章能不能留住读者？ | 风格 |
| 情节推进 | 这章有事发生吗？还是水了一章？ | 逻辑 |
| 人物塑造 | 角色立体吗？还是纸片人？ | 角色 |
| 对话质量 | 对话有目的吗？还是"你好吃了么"？ | 角色 |
| 悬念设置 | 章尾留钩子了吗？ | 逻辑 |
| 节奏控制 | 张弛有度吗？还是一味快/一味慢？ | 节奏 |
| 展示而非讲述 | 是"show"还是"tell"？ | 风格 |
| 语言质量 | 有没有 AI 味？成语堆砌？ | 风格 |
| 题材适应度 | 符合这个类型的读者预期吗？ | 设定 |
| 跨章连贯性 | 和上一章接得上吗？ | 连续 |

**还有额外的加分项——根据题材动态加的：**

- 悬疑/推理：线索布局、谜题逻辑、信息揭示、误导设计
- 言情：关系张力、情感节奏、CP 化学反应、冲突真实性
- 奇幻/科幻：世界观一致性、新奇感、设定融入、规则代价
- 成长励志：成长可见性、挫折真实性、顿悟时刻
- 动作冒险：动作描写、紧张感递进、后果意义

**还有一个"红线扫描"——纯规则检测，不调 AI：**

如果你给某个角色设了禁忌（比如"主角绝不哭泣"），系统会用正则表达式扫描正文，一旦发现违规，直接标为"阻断"级别。

### 5.4 评分不够怎么办？（修复闭环）

质检完有一个总分（满分 100 分），根据分数决定命运：

```
总分 >= 60（标准题材）/ 65（严格题材：悬疑/奇幻）且没有问题 → PASS（合格，直接保存）
总分 >= 阈值 - 10                                          → WARNING（勉强过关，保存但不修复）
总分 < 阈值 - 10                                           → NEEDS_FIX（不及格，进入修复）
有任何阻断级问题                                            → BLOCKED（强制修复）
```

**修复分两种：**

| 情况 | 修复方式 | 温度 | 策略 |
|------|----------|------|------|
| 分数接近及格线（离阈值 ≤ 10 分） | Patch Repair（小修） | 0.5 | "只改有问题的段落，其他地方别动" |
| 分数差得远（离阈值 > 10 分） | Heavy Repair（大修） | 0.7 | "全面重写，但保住章节任务和角色状态" |

修复完**重新打分**，如果通过了就算过关。

### 5.5 Agent 挂了怎么办？（降级策略）

每个 Agent 都有兜底方案：

| Agent | 挂了/出错了怎么办 |
|-------|-----------------|
| ContextAgent | 返回极简简报（从原始数据里拼几条） |
| ReviewerAgent | 重试 2 次 → 每维度默认 5 分 |
| DataAgent | 返回空数组 + 章节前 500 字当摘要 |

## 六、Token 预算——AI 的"注意力有限"

### 6.1 为什么要管 Token？

AI 模型的"注意力"是有限的。GPT-4 的上下文窗口大约是 128K tokens，但系统只敢用 **70%**（约 89,600 tokens），剩下 30% 留给：

- System prompt（指令，约 2000-5000 tokens）
- 写作技巧注入（根据章节位置动态添加 5-10 条原则）
- 格式开销
- 给 AI 留出回复空间

### 6.2 上下文从哪来？

写一章之前，系统要从 **20+ 个模块** 收集参考资料，每个模块产生一个"上下文块"：

| 上下文块 | 从哪来 | 优先级 |
|---------|--------|--------|
| 本书合约 | 你创建小说时填的故事核心 | 104（最高） |
| 本章任务 | 大纲里给这章定的目标 | 100 |
| 上一章内容 | 上一章的正文 | 100 |
| 角色硬事实 | 所有角色的当前状态 | 99 |
| 伏笔指令 | 待回收的伏笔 | 98 |
| 内容节拍 | 本章应该有什么节奏 | 98 |
| 卷级导向 | 当前卷的大方向 | 98 |
| 角色关系动态 | 角色间的情感变化 | 97 |
| 期待链 | 对标书中读者期待模式的分析 | 96 |
| 实体生命周期 | 谁死了、谁活了、谁消失了 | 95 |
| 世界规则 | 当前激活的世界观规则 | 90 |
| 语义记忆 | 笔记本里的记忆 | 92 |
| 开放冲突 | 还没解决的冲突 | 88 |
| 时间线 | 过去 8 个事件 + 未来 5 个 | 85 |
| RAG 回溯 | 从历史章节语义搜索的结果 | 85 |
| 对标书范例 | 类似章节的开头/结尾写法 | 77 |
| 写作技巧 | 对标书分析的写作规则 | 76 |
| 风格合同 | 你上传的对标书的风格特征 | 74 |
| 最近章节 | 前 3 章的详细片段 | 86 |
| 更早章节 | 骨架摘要 | 80 |
| 上一卷摘要 | 上一卷的 LLM 总结 | 82 |
| ... | 更多... | 更低 |

### 6.3 如果东西太多了怎么办？（三层截断）

20+ 个模块加起来肯定超 token 预算，系统有一套智能裁剪策略：

```
按优先级排序后，逐个处理：
    │
    ├── 优先级 >= 90 → 保留（必须看）
    │   比如：本书合约、本章任务、角色硬事实
    │
    ├── 60 <= 优先级 < 90 → 摘要（压缩后保留）
    │   按段落边界切，能塞多少塞多少
    │   末尾加 "...[摘要截断]" 标记
    │
    └── 优先级 < 60 → 丢弃（不看）
        比如：craft_stats（71 分）、writing_techniques（76 分）
        如果预算紧张，这些会被先砍掉
```

### 6.4 新鲜度衰减——"越近的信息越重要"

同样的优先级，**越近的章节内容越应该被保留**。系统用一个公式解决这个问题：

```
有效优先级 = 原始优先级 × 新鲜度衰减系数
衰减系数 = 1 / (1 + 距离章节数 / 衰减率)
```

**举例：**

- 角色状态块，原始优先级 99，衰减率 20（变化快）
  - 距离当前 20 章 → 有效优先级 = 99 × 0.5 = 49.5（减半！）
  - 距离当前 5 章 → 有效优先级 = 99 × 0.8 = 79.2（基本保持）

- 世界规则块，原始优先级 90，衰减率 100（变化慢）
  - 距离当前 50 章 → 有效优先级 = 90 × 0.67 = 60.3（几乎不变）

- 风格合同块，原始优先级 74，衰减率 ∞（永不衰减）
  - 无论多远，优先级不变

### 6.5 不同类别的衰减率

| 衰减率 | 代表哪些信息 | 为什么 |
|--------|------------|--------|
| ∞（永不衰减） | 风格、合约、任务、上一章 | 永远有效 |
| 200 | 远古卷归档 | 太远了但偶尔有用 |
| 100 | 世界规则 | 世界观很少变 |
| 80 | 卷摘要、宏观故事 | 相对稳定 |
| 50 | 伏笔、期待链、RAG | 中等时效 |
| 30 | 时间线、最近章节 | 近期重要 |
| 20 | 角色状态、关系 | 变化最快 |

## 七、结构化输出自愈——AI 说人话的翻译器

### 7.1 什么问题？

系统经常让 AI 输出 JSON（比如质量评分、事实提取），但 AI 经常输出格式错误的 JSON：

- 忘了闭合括号
- 用了错误的字段名
- 把数字写成了字符串
- 返回了数组而不是对象
- 把 `null` 写成 `undefined`

### 7.2 六阶段修复管线

系统在把 AI 的输出交给系统之前，先做 6 轮"整形手术"：

```
AI 吐出来的原始文本
    │
    ├── 第 0 轮：JSON 提取 + 截断闭合
    │   去掉 markdown 代码块标记 ```json ... ```
    │   如果 AI 话说一半被截断了（比如 token 用完了），自动补齐缺失的括号/方括号
    │
    ├── 第 1 轮：类型归一
    │   "5" → 5, "true" → true, 5 → "5"
    │   递归处理嵌套对象
    │
    ├── 第 1.5 轮：字段名修复
    │   AI 用了 "rule" 但系统期望 "content" → 自动映射
    │   排除元数据字段（category/title/name/id/type/status 等不参与映射）
    │
    ├── 第 2 轮：数组包裹/解包
    │   系统要对象，AI 给了数组 → 包一层
    │   系统要单个对象，AI 给了数组 → 拆出来
    │
    ├── 第 3 轮：null → undefined
    │   AI 喜欢用 null 表示"没有"，但系统期望 undefined（Zod 的 .optional() 不接受 null）
    │
    ├── 第 4 轮：超大数组截断
    │   系统期望最多 10 个，AI 给了 20 个 → 砍到 10 个
    │
    └── 第 5 轮：如果以上全失败 → 带错误信息重试 AI
        把 Zod 校验错误翻译成中文告诉 AI，让它自己改
        最多重试 3 次
```

**关键点：** 前 4 轮是纯代码层面的修复（不花钱），只有全部失败才重新调 AI（花钱）。

## 八、分层压缩——"读书笔记"式的长期记忆

### 8.1 问题

写到第 200 章的时候，如果把前 199 章全部塞给 AI，token 根本不够用。

### 8.2 解决方案：5 层压缩

```
第 200 章的上下文窗口里，关于"以前发生了什么"的部分：

第 1 层：最近 3 章 → 详细片段（每章 ~500 字）
         "这是最珍贵的，不能丢"
    │
第 2 层：第 4-10 章 → 骨架摘要（每章 ~200 字）
         "只保留关键情节，去掉描写"
    │
第 3 层：上一整卷 → 完整摘要（~2000 字）
         "LLM 总结的卷级摘要"
    │
第 4 层：更早的卷 → 每卷 1-2 句话
         "远古记忆，知道有过这回事就行"
    │
第 5 层：超远古 → 一行 digest
         "这本书以前有个 XXX 卷"
```

### 8.3 自动压缩

每写 10 章，系统会自动触发一次 LLM 压缩，把前 10 章浓缩成一个结构化摘要，包含：

- 关键事件
- 角色变化
- 世界观揭示
- 未回收的伏笔

## 十、伏笔管理系统——"别忘了你答应过读者什么"

### 10.1 伏笔是什么？

网文里经常说"伏笔"——前面埋一个线索，几十章后再回收。

比如第 5 章写"他在废墟中发现了一块刻着奇怪符号的石碑"，然后作者忘了。写到第 100 章才想起来这块石碑很重要，需要回收。

### 10.2 系统怎么管的？

系统有一个 `PayoffLedgerItem` 表专门管伏笔：

| 状态 | 含义 |
|------|------|
| setup | 刚设定，还没开始铺垫 |
| hinted | 已经开始暗示了 |
| pending_payoff | 快到回收时间了 |
| paid_off | 已回收 |
| overdue | 过期了（超目标章节 3 章以上没回收） |
| failed | 失败了（超目标章节 10 章以上） |

每写完一章，系统自动检查有没有过期的伏笔，并给作者发提醒。

### 10.3 写作时的伏笔指令

写每一章的时候，系统会把当前活跃的伏笔作为上下文块注入给 AI（`payoff_directives`，优先级 98），告诉 AI："这里有几个伏笔等着回收，本章要考虑处理"。

## 十一、时间线系统——"别搞错时间顺序"

### 11.1 问题

写到第 100 章的时候，AI 很容易搞混：

- "张三不是说上个月去了京城吗？怎么这章又在南方？"
- "大比不是三个月后才举行吗？怎么这章就开始了？"

### 11.2 解决方案

每写完一章，系统自动提取时间线事件：

```
第 N 章正文
    │
    ▼
LLM 提取时间线事件：
  - "三月十五，张三到达青云宗"
  - "距离大比还有 30 天"
  - "李四的伤需要三个月恢复"
    │
    ▼
存入 TimelineItem 表
    │
    ▼
检测冲突：
  - 顺序冲突（先到了京城再去青云宗？）
  - 逻辑冲突（同时出现在两个地方）
  -  deadline 冲突（大比已经过了但没提）
  - 重复事件（同一件事写了两次）
```

写下一章的时候，系统会把过去 8 个时间线事件 + 未来 5 个即将发生的事件注入给 AI。

## 十二、风格系统——"模仿对标书的写法"

### 12.1 你上传一本书作为"对标书"

比如你想写《斗破苍穹》风格的小说，就把《斗破苍穹》上传到系统。

### 12.2 系统分析对标书的风格特征

LLM 会分析对标书的：

- 叙事方式（第一人称/第三人称，上帝视角/跟随视角）
- 语言风格（朴实/华丽/口语化/书面化）
- 角色塑造手法
- 节奏特点
- 反 AI 特征（避免哪些 AI 常见的写法）

### 12.3 自动检测 AI 写作痕迹

系统有一个规则引擎，检测 7 类 AI 痕迹：

1. **AI 高频词汇**：璀璨、心潮澎湃、油然而生、不禁
2. **成语堆砌**：连续使用两个以上四字成语
3. **模式重复**：句式/段落结构反复雷同
4. **密度稀释**：信息量过低，全是废话
5. **连接词滥用**：然后、接着、于是、随后
6. **总结句**：每段结尾来一句"这让我明白了..."
7. **独白比例过高**：内心戏太多

## 十五、技术栈详解——每个技术是什么、为什么选它、怎么用

> 这一章是给面试准备的。面试官可能会问"你们为什么用 React 不用 Vue？""Prisma 是什么？""SQLite 能扛住吗？"，下面的内容帮你用大白话回答这些问题。

---

### 15.1 React 19 — 用户界面的"积木框架"

**一句话定义：** React 是一个构建用户界面的 JavaScript 库，核心思想是把页面拆成一个个"组件"（像乐高积木），每个组件管自己的 UI 和状态。

**基本原理：**
- **组件化**：页面 = 组件树。比如"章节列表"是一个组件，"编辑器"是一个组件，"质检面板"是一个组件。每个组件只管自己的那块区域。
- **虚拟 DOM**：React 不在内存里建一份"虚拟页面"，每次数据变化时先算"哪里变了"，再只更新变化的部分。这比直接操作真实 DOM 快得多。
- **Hooks**：React 16.8 引入的函数式编程模式，让函数组件也能管理状态（useState）和副作用（useEffect）。React 19 进一步简化了 async/await 的支持。
- **并发渲染（Concurrent Rendering）**：React 18+ 把渲染拆成小块，中间可以暂停去处理高优先级任务（比如用户点击），不会卡界面。

**为什么选 React：**
- 生态最成熟，组件库最多（Tailwind、Lucide、Sonner 都是 React 生态的）
- TypeScript 支持最好，类型推导几乎零配置
- 声明式编程（"描述想要什么样子"而不是"一步步怎么改"），代码好读好维护

**在项目中的用法：**
- 纯函数组件 + Hooks，没有 Redux/Context 之类的重量级状态管理
- 唯一的 Provider 是 `QueryClientProvider`（TanStack Query）和 `RouterProvider`（React Router）
- 页面级路由：StartPage → NovelsPage → NovelWorkspacePage（写作工作台）/ PlanningHubPage（大纲中心）

---

### 15.2 Vite 7 — 前端项目的"秒开构建工具"

**一句话定义：** Vite 是一个前端构建工具，负责把你的源代码打包成浏览器能跑的静态文件。

**基本原理：**
- **开发模式**：Vite 不用打包，直接让浏览器原生加载 ES Module（ESM）。浏览器自己懂怎么拉取和解析模块，所以启动几乎是秒开的。相比之下 Webpack 开发时要先把所有代码打包一遍，慢十几秒到几分钟。
- **生产模式**：Vite 用 Rollup 做打包，会把所有代码压缩、混淆、树摇（去掉没用到的代码），生成最小的生产文件。
- **插件系统**：React 支持靠 `@vitejs/plugin-react` 插件，CSS 预处理靠其他插件。

**为什么选 Vite：**
- 冷启动速度碾压 Webpack（本项目开发模式下 Vite 在 7457 端口启动，秒开）
- 配置极简，`vite.config.ts` 只有几行
- 内置 TypeScript 支持，不需要额外配置

**在项目中的用法：**
- 开发时：Vite 代理 `/api` 到后端 7456 端口，前后端联调不走跨域
- 生产构建：通过 `ONE2NOVEL_CLIENT_BASE=relative` 环境变量切换资源路径为相对路径，适配 Electron 的 `loadFile()` 加载本地 HTML

---

### 15.3 Tailwind CSS — "直接在 HTML 里写样式"

**一句话定义：** Tailwind 是一个原子化 CSS 框架，用一个个小 class（如 `bg-blue-500`、`p-4`、`flex`）来组合出样式，不再写单独的 `.css` 文件。

**基本原理：**
- 传统 CSS：写一个 `.btn-primary { ... }` 类名，然后在 HTML 里引用。类名和样式是分离的。
- Tailwind：直接在 HTML 标签上加 class，比如 `class="bg-blue-500 text-white rounded-lg p-4 hover:bg-blue-600"`，样式和结构在一起。

**为什么选 Tailwind：**
- 不用纠结类名命名（传统 CSS 最大的痛苦：给按钮起什么名字？）
- 设计系统一致，间距/颜色/字号都是预设的，不会出现"这个 padding 用 16px 还是 20px"的争论
- 生产构建时自动去掉没用的 class，打包体积很小

**在项目中的用法：** `client/src/components/` 下所有组件都用 Tailwind class，配合 `clsx` 和 `tailwind-merge` 做条件样式合并。

---

### 15.4 TipTap — "看不见的外壳，看得见的编辑器"

**一句话定义：** TipTap 是一个 Headless（无头/无界面）富文本编辑器，基于 ProseMirror 构建，让你自己决定编辑器长什么样。

**基本原理：**
- **Headless**：TipTap 不提供任何 UI 按钮（粗体、斜体等），它只管理编辑器的内容和状态。你想做什么样的工具栏就自己做。
- **基于 ProseMirror**：底层是一个强大的文档编辑引擎，支持复杂的文档模型（段落、列表、表格、自定义节点）。
- **扩展系统**：通过安装扩展（Extension）来添加功能，比如 `starter-kit` 提供基础排版，`placeholder` 提供占位符文字。

**为什么选 TipTap：**
- Headless 架构意味着编辑器 UI 完全可控，可以做出和小说创作场景高度匹配的界面
- 比 Quill/Slate 更现代，TypeScript 支持更好
- 导出 Markdown 原生支持（小说内容存 Markdown 格式）

**在项目中的用法：** 写作工作台（ChapterWritePanel）的核心编辑器，用户写的章节正文存在 TipTap 编辑器里，导出时转为 Markdown。

### 15.5 TanStack Query — "服务端状态的管家"

**一句话定义：** TanStack Query（原名 React Query）是一个管理"从服务器来的数据"的库，负责缓存、自动刷新、加载状态、错误处理。

**基本原理：**
- 传统做法：用 `useEffect` + `useState` 手动 fetch 数据，自己管 loading/error/缓存。每个页面都要写一遍。
- TanStack Query：你只需要告诉它"我要什么数据"（queryKey）和"去哪拿"（URL），它自动管缓存、重试、失效刷新。

**为什么选它：**
- 不用自己写 loading/error 状态机，代码量减少 70% 以上
- 自动缓存：同一份数据多个组件共享，避免重复请求
- 自动失效：数据变更后调用 `invalidateQueries()`，下次访问时自动刷新

**在项目中的用法：**
- 全局配置：30 秒 stale time（超过 30 秒认为数据过期）、查询失败重试 1 次、mutation 不重试（因为是破坏性操作）
- 工厂模式：`createQueryHook` 工厂函数，大多数 hook 只需 3-5 行配置

### 15.6 Express 5 — "Node.js 的 HTTP 路由框架"

**一句话定义：** Express 是一个 Node.js 后端框架，负责接收 HTTP 请求、路由到处理函数、返回响应。

**基本原理：**
- **中间件模式**：请求进来时经过一连串"中间件"（middleware），每个中间件可以做一件事（解析 JSON、记录日志、安全检查），最后到达路由处理器。
- **Router**：把相关的路由组织在一起，比如所有 `/novels/*` 的请求走同一个 Router。

**为什么选 Express：**
- Node.js 生态最成熟的 HTTP 框架，文档和社区资源最丰富
- 轻量灵活，不强制架构风格
- 中间件生态极其丰富（helmet 安全、cors 跨域、compression 压缩）

**在项目中的用法：**
- `createApp()` 组装中间件链（helmet → cors → json parser → 路由）
- `registerRoutes()` 挂载所有子路由
- 全局错误处理：`errorHandlerWrap()` 替代了 127+ 个裸 catch 块

### 15.7 Prisma 7 — "把数据库操作变成 TypeScript 函数"

**一句话定义：** Prisma 是一个 TypeScript ORM（对象关系映射器），让你用类型安全的 TypeScript 代码操作数据库，而不是写 SQL。

**基本原理：**
- **Schema 驱动**：你在 `schema.prisma` 文件里用声明式语法定义数据模型（表结构），Prisma 自动生成对应的 TypeScript 类型和查询方法。
- **类型安全**：当你写 `prisma.chapter.findMany()` 时，IDE 会提示你有哪些字段、返回什么类型。字段名写错了编译期就报错。
- **适配器模式**：Prisma 本身不直接操作数据库，通过"适配器"（Adapter）桥接不同的数据库引擎。本项目用 `@prisma/adapter-better-sqlite3` 连接 SQLite。

**为什么选 Prisma：**
- 类型安全：前后端共用同一套类型定义（通过 `shared/` 包），不会出现"前端传了 `userName` 后端查的是 `username`"的 bug
- 开发效率高：`prisma generate` 自动生成客户端，不需要手写 CRUD
- 迁移系统成熟：虽然本项目没用迁移（用了 template DB 策略），但 Prisma 的迁移系统是整个行业最好的

**在项目中的用法：**
- `server/prisma/schema.prisma` 定义数据模型
- `server/src/platform/db/client.ts` 初始化 PrismaClient 单例
- 模板数据库策略：不用 Prisma migrate，启动时用预构建的 `template.db`，`ensureSchema()` 对比已有表和模板的差异，只 ADD 不 DROP（保护用户数据）

### 15.8 SQLite + better-sqlite3 — "一个文件的数据库"

**一句话定义：** SQLite 是一个嵌入式的关系型数据库，不需要单独安装服务器，整个数据库就是一个文件。`better-sqlite3` 是 Node.js 下 SQLite 的高性能同步驱动。

**基本原理：**
- **嵌入式**：不像 MySQL/PostgreSQL 需要一个单独的数据库服务器进程，SQLite 直接读磁盘文件。调用方式就是 `new Database('my.db')`。
- **ACID 事务**：虽然是轻量级数据库，但完整支持事务的原子性、一致性、隔离性、持久性。
- **同步 API**：`better-sqlite3` 提供同步阻塞 API（不用写 async/await），在 Electron 主线程中性能更好。

**为什么选 SQLite：**
- 零运维：一个 `.db` 文件，备份就是复制文件，恢复也是复制文件
- 桌面端场景完美匹配：One2Novel 是 Electron 桌面应用，数据和应用在同一台机器上，不需要网络数据库
- 百万字小说的数据量完全够用（SQLite 支持 TB 级数据库）
- RAG 向量库也用 SQLite（独立 `rag_vectors.db` 文件），不增加主库负担

**在项目中的用法：**
- 主数据库：`dev.db`，存储小说/章节/角色/记忆等业务数据
- RAG 数据库：`rag_vectors.db`，存储向量数据和 BM25 倒排索引
- 通过 Prisma ORM 操作，应用层不直接接触 SQL

### 15.9 LangChain — "AI 模型的万能遥控器"

**一句话定义：** LangChain 是一个 AI 应用开发框架，提供统一的接口调用不同的 LLM（大语言模型），让你不用为每个 AI 服务商写一套代码。

**基本原理：**
- **统一接口**：无论是 DeepSeek、OpenAI、Claude 还是 Gemini，LangChain 都暴露相同的 `invoke(messages)` 方法。换提供商只需要改配置，不改代码。
- **Message 类型**：系统消息（SystemMessage，告诉 AI 角色和规则）、用户消息（HumanMessage，实际的问题/指令）、AI 消息（AIMessage，AI 的回答）。这些类型跨所有提供商通用。
- **Streaming**：LangChain 内置流式输出支持，AI 每生成一个 token 就推送出来，不需要自己实现 SSE 解析。

**为什么选 LangChain：**
- 多提供商支持：本项目支持 6 个提供商（DeepSeek、OpenAI、Anthropic、Gemini、Qwen、Moonshot），如果用原生 SDK 要为每个写一套代码
- 标准化消息格式：System/Human/AIMessage 在所有提供商间通用
- 自带 token 用量统计：不同提供商的 token 计数位置不同（OpenAI 在 `response_metadata.tokenUsage`，Anthropic 在 `response_metadata.usage`），LangChain 统一了

**在项目中的用法：**
- `createLLM(provider, options)` 工厂函数根据提供商类型实例化对应的 LangChain 聊天类
- `aiInvoke()` / `invokeAsset()` 是上层封装的服务，统一处理 prompt 解析、上下文选择、结构化输出修复
- 三种提供商族：OpenAI 兼容（ChatOpenAI）、Anthropic（ChatAnthropic）、Google（ChatGoogleGenerativeAI）

### 15.10 Zod 4 — "运行时类型检查的守门员"

**一句话定义：** Zod 是一个 TypeScript 优先的 Schema 验证库，可以在运行时（程序跑的时候）检查数据是否符合你定义的规则。

**基本原理：**
- **Schema 即代码**：你用 TypeScript 语法写验证规则，比如 `z.string().min(1).max(100)` 表示"必填字符串，最长 100 字符"。
- **类型双向推导**：从 Zod Schema 可以反向推导 TypeScript 类型（`z.infer<typeof schema>`），也可以从 TypeScript 类型生成 Zod Schema。前后端共用同一套定义。
- **运行时验证**：程序跑的时候，Zod 检查实际传入的数据是否合法，不合法就抛错。

**为什么选 Zod：**
- TypeScript 生态的事实标准，类型推导最准确
- 本项目有两个用途：① API 输入验证（检查前端传来的数据对不对）② LLM 输出类型定义（告诉 AI 应该返回什么格式的 JSON）
- 比 Joi/Yup 更现代，API 更简洁

**在项目中的用法：**
- `shared/types/novel.ts` 定义所有 Schema，client 和 server 都 import 同一个文件
- API 路由：`NovelCreateSchema.parse(req.body)` 验证请求体
- LLM 调用：把 Zod schema 传给 `aiInvoke()`，AI 输出的 JSON 自动按 schema 验证和修复

### 15.11 Electron 35 — "用 Web 技术写桌面应用"

**一句话定义：** Electron 是一个框架，让你用 HTML/CSS/JavaScript（Web 技术）构建跨平台桌面应用。底层是 Chromium 浏览器 + Node.js 运行时。

**基本原理：**
- **双进程模型**：
  - **Main Process（主进程）**：Node.js 环境，管理窗口、文件系统、启动后端服务器。相当于"管理员"。
  - **Renderer Process（渲染进程）**：Chromium 浏览器，渲染 React 页面。相当于"前台"。
- **Context Bridge（上下文桥）**：出于安全考虑，渲染进程默认不能直接访问 Node.js API。通过 `contextBridge.exposeInMainWorld()` 暴露一个安全的接口，让前端能拿到后端传的配置。
- **Context Isolation（上下文隔离）**：Electron 默认开启的安全特性，防止恶意脚本注入。

**为什么选 Electron：**
- 一套代码跑 Windows/Mac/Linux，不需要学 C++/Swift/Kotlin
- 可以嵌入后端服务器（本项目把 Express server 打包进 Electron），做成"自带数据库"的离线应用
- 生态成熟：`electron-builder` 打包 NSIS 安装包，`electron-updater` 自动更新

**在项目中的用法：**
- 主进程：启动 BrowserWindow、单实例锁、健康检查等待后端就绪、`utilityProcess.fork()` 启动嵌入式服务器
- Preload 脚本：读取 `ONE2NOVEL_DESKTOP_RUNTIME` 环境变量，注入 `window.__ONE2NOVEL_RUNTIME__` 给渲染进程
- 路由模式：桌面端用 hash 路由（`#/novels`），因为 `loadFile()` 加载本地 HTML 时 pushState 路由会 404

### 15.12 SSE (Server-Sent Events) — "AI 打字效果的传输协议"

**一句话定义：** SSE 是浏览器内置的一种单向实时通信协议，服务端可以主动向客户端推送消息，不需要轮询。

**基本原理：**
- 客户端发起一个普通 HTTP 请求，但带上 `Accept: text/event-stream` 头。
- 服务端不关闭连接，持续往这个连接推送数据，每条数据以 `\n\n` 分隔。
- 每条消息可以有 `event:` 类型和 `data:` 内容。

**为什么用 SSE 而不是 WebSocket：**
- AI 写作只需要**服务端→客户端**的单向推送（AI 写一个字，推一个字到编辑器），不需要客户端→服务端的双向通信
- SSE 自动重连、自动心跳、兼容所有 HTTP 中间件
- WebSocket 是全双工的（两端都能发消息），用在那里是大材小用

**在项目中的用法：**
- 前端用 `fetch` + `ReadableStream` 手动解析 SSE（不用 `EventSource` API，因为需要 POST 请求带 body）
- 事件类型：`stage`（当前阶段）、`token`（生成的文字）、`heartbeat`（心跳保活）、`complete`（完成）、`error`（错误）
- 容错：30 秒无心跳自动保存草稿到 localStorage；每 50 个 token 自动保存

### 15.13 pnpm Monorepo — "一个仓库管四个包"

**一句话定义：** pnpm 是一个 Node.js 包管理器，配合 workspaces 功能可以管理一个包含多个子项目的"单体仓库"（Monorepo）。

**基本原理：**
- **硬链接（Hard Links）**：pnpm 不用 `node_modules` 的嵌套目录结构，而是把所有包硬链接到一个中央存储。节省磁盘空间，加快安装速度。
- **Workspaces**：一个 `package.json` 里声明多个子包（client/server/shared/desktop），它们可以互相引用（`"@one2novel/shared": "workspace:*"`）。
- **严格依赖隔离**：每个子包只能 `import` 自己 `package.json` 里声明的依赖，不会偷偷用到兄弟包的依赖。

**在项目中的用法：**
- 4 个 workspace：`@one2novel/shared`（共享类型）、`@one2novel/server`（后端）、`@one2novel/client`（前端）、`@one2novel/desktop`（桌面包装）
- 构建顺序：shared → server → client（依赖顺序）
- 开发命令：`pnpm dev` 同时启动 server + client

## 十六、关键设计决策

### 为什么用 SQLite 而不是 PostgreSQL？

- 单人项目，不需要分布式
- SQLite 零运维，一个文件搞定
- 百万字小说的数据量完全够用
- RAG 也独立存 SQLite，不增加主库负担

### 为什么 RAG 不用 Milvus/Weaviate？

- 同样原因：零运维优先
- 自建 BM25 不依赖任何外部服务
- embedding 挂了 BM25 还能用
- 等用户量上来了再考虑迁移

### 为什么记忆系统用一张表而不是多张？

- 7 种记忆类别本质上是"标签"不同
- 用同一个表 + 分类查询更灵活
- 去重逻辑统一（按类别+主体+字段）
- 后期加新类别不需要改数据库结构

### 为什么 post-write 用事件总线而不是直接调用？

- 11 个任务互不依赖，可以并行
- 任何一个失败都不影响主线
- 方便后期加新任务（只需要注册 handler）
- 用信号量控制并发（最多 3 个），防止 SQLite 锁竞争

## 十七、Monorepo 架构——四个包怎么协作

```
┌─────────────────────────────────────────┐
│  root package.json (pnpm workspaces)    │
│                                         │
│  ┌──────────┬──────────┬───────────┐   │
│  │ shared   │  server  │  client   │   │
│  │ (Zod     │ (Express │ (React    │   │
│  │ schemas) │  +       │  + Vite)  │   │
│  └────┬─────┴────┬─────┴─────┬─────┘   │
│       │          │           │          │
│       └──────────┼───────────┘          │
│                  ▼                       │
│          ┌─────────────┐                │
│          │   desktop   │                │
│          │ (Electron   │                │
│          │  bundles    │                │
```

- **shared**：前后端共用的 Zod Schema 和 TypeScript 类型。改一处，两边都生效。

## 十八、Desktop vs Web 双模式——一套代码两种运行方式

同一套 React 代码，既可以跑在浏览器里（Web 模式），也可以打包进 Electron（Desktop 模式）。区别在于：

**检测链路：**
1. Electron preload 脚本注入 `window.__ONE2NOVEL_RUNTIME__`（JSON 配置）
2. React 读取这个对象，判断 `APP_RUNTIME === "desktop"`
3. 根据 runtime 类型自动切换：

| 切换项 | Web 模式 | Desktop 模式 |
|--------|---------|-------------|
| 路由模式 | BrowserRouter（history API） | HashRouter（`#/novels`） |
| API 地址 | `/api`（同源代理） | `http://localhost:7456/api`（嵌入式服务器） |
| 资源路径 | `/`（绝对路径） | `./`（相对路径） |
| 自动更新 | 不适用 | electron-updater 检查更新 |

**为什么桌面端用 Hash 路由：** Electron 的 `loadFile()` 加载本地 `index.html` 时，如果 URL 里有路径（如 `#/novels`），浏览器会尝试请求 `/novels.html` 文件导致 404。Hash 路由把路径放在 `#` 后面，浏览器不把它当路径请求，所以不会 404。

## 十九、Prompt Registry 模式——AI 提示词的集中管理

**问题：** 如果每个 route handler 里都写一段 system prompt 字符串，会有 20+ 处重复的提示词，改一个要改 20 个文件。

**解决方案：** 所有 AI 提示词集中在 `promptRegistry`（一个 `Map<string, PromptAssetDef>`）里管理：

- **注册**：每个模块在 `server/src/modules/novel/prompts/*.ts` 里通过 `promptRegistry.register()` 注册自己的提示词，带 `id`、`taskType`、`version`、`systemPrompt`
- **调用**：服务层只传 `assetId`（如 `"chapter.writer.v1"`），系统自动从 registry 找到对应的提示词
- **动态注入**：`aiInvoke()` 自动注入 format hint（从 Zod schema 自动生成输出约束）、skill rules（写作技巧原则，根据章节位置动态选择 5-10 条）

**Task-Type 模型路由：** 每种任务类型有预设的 temperature 和 maxTokens：

| TaskType | Temperature | Max Tokens | 为什么 |
|----------|------------|------------|--------|
| Writer | 0.85 | 8192 | 创作需要创造性 |
| Reviewer | 0.3 | 2048 | 质检需要严谨 |
| Planner | 0.8 | 8192 | 规划需要发散 |
| Extractor | 0.5 | 4096 | 提取需要平衡 |
| Compiler | 0.3 | 2048 | 编译需要精确 |
| Repairer | 0.5 | 8192 | 修复需要一定创造性 |

## 二十、Event Bus 事件驱动架构——11 个后台任务的并行管道

**问题：** 每写完一章需要做 11 件不同的事（时间线提取、摘要生成、RAG 入库、压缩、反 AI 检测、角色更新、记忆沉淀、伏笔检查、完成度检查、卷完结审计、债务利息计算），如果串行执行会很慢，而且任何一个失败都会阻塞下一章。

**解决方案：** 事件总线 + 信号量限流

```
chapter.saved 事件
    │
    ▼
Promise.allSettled([  ← 11 个 handler 并行执行
    timeline, summary, ragIndex, volumeCompress,
    antiAi, characterState, memory, payoff,
    completion, volumeCompletion, debtInterest
])
    │
    ▼
Semaphore(3)  ← 最多 3 个并发，防止 SQLite 锁竞争
```

- **fire-and-forget**：所有 handler 都是 `Promise.allSettled()`，任何一个失败不影响其他
- **信号量限流**：`POST_WRITE_MAX_CONCURRENT = 3`，每个 handler 执行前获取一个信号量槽位
- **懒加载**：用 `await import()` 动态导入模块，避免启动时加载所有代码
- **跳过机制**：如果 `ChapterCommit.projectionStatus === 'completed'`（投影写入器已处理），则跳过对应 handler，避免重复写入

## 二十一、Prisma Template DB 策略——不用 Migration 的数据库管理

**问题：** Prisma 的标准做法是用 `prisma migrate` 管理数据库变更（migration files）。但桌面应用的用户数据库在本地，远程跑 migration 不现实。

**解决方案：** 预构建模板数据库 + 差异检测

1. 开发者维护一个 `prisma/template.db`（预建好所有表结构）
2. 应用启动时 `ensureSchema()` 检查用户数据库是否存在
3. 如果存在，对比 template.db 和用户 DB 的表结构，**只 ADD 不 DROP**（新增列/表，不修改不删除）
4. 如果不存在，复制 template.db 作为用户数据库

**优点：** 零 migration 文件、冷启动快（直接复制模板库）、用户数据不会被误删。

## 二十二、Token Budget 三级裁剪——AI 注意力不够怎么办

写一章之前要收集 20+ 个上下文模块，加起来远超 AI 的上下文窗口。系统用三级裁剪策略控制总 token 数在预算内（128K × 70% ≈ 89,600 tokens）：

```
按优先级排序后逐个处理：
    │
    ├── 优先级 >= 90 → 完整保留（FORCE KEEP）
    │   例如：本书合约(104)、本章任务(100)、上一章内容(100)
    │
    ├── 60 ≤ 优先级 < 90 → 摘要压缩（SUMMARIZE）
    │   按段落边界切，能塞多少塞多少
    │   末尾加 "...[摘要截断]" 标记
    │
    └── 优先级 < 60 → 丢弃（DROP）
        例如：craft_stats(71) 在预算紧张时会被砍掉
```

## 二十三、Freshness Decay 新鲜度衰减——越近的信息越重要

同样的优先级，**越近的内容越应该被保留**。系统用一个公式解决这个问题：

```
有效优先级 = 原始优先级 × 衰减系数
衰减系数 = 1 / (1 + 距离章节数 / 衰减率)
```

不同信息类型的衰减率不同（变化越快，衰减越快）：

| 衰减率 | 代表信息 | 原因 |
|--------|---------|------|
| ∞（永不衰减） | 风格、合约、任务、上一章 | 永远有效 |
| 200 | 远古卷归档 | 太远了但偶尔有用 |
| 100 | 世界规则 | 世界观很少变 |
| 80 | 卷摘要、宏观故事 | 相对稳定 |
| 50 | 伏笔、期待链、RAG | 中等时效 |
| 30 | 时间线、最近章节 | 近期重要 |
| 20 | 角色状态、关系 | 变化最快 |

**举例：** 角色状态块原始优先级 99，衰减率 20。距离当前 20 章时，有效优先级 = 99 × 0.5 = 49.5（减半！）。而世界规则块原始优先级 90，衰减率 100。距离 50 章时，有效优先级 = 90 × 0.67 = 60.3（几乎不变）。
